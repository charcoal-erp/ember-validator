# Ember Bundle Format — Specification

**Version:** `1.0` — **FROZEN 2026-08-01** (reviewed and approved by the owner; any further
normative change requires a new minor/major version via owner-approved PR)
**File extension:** `.czx` (Charcoal eXchange)
**Owner:** Charcoal ERP. Every normative change to this document lands as a pull request
approved by the owner; the change process is described in §14.
**Reference validator:** [`ember-validator`](https://github.com/charcoal-erp/ember-validator) (`ember-validate verify <bundle>`), written
against this document and kept independent of any exporter/importer implementation.

This specification is self-contained: a third party writing an adapter that produces or
consumes bundles needs only this document and the validator. Key words **MUST**, **MUST NOT**,
**SHOULD**, **MAY** are RFC 2119.

---

## 1. Overview and terminology

An **Ember bundle** is a self-describing archive that carries one organization's data out of —
or into — a Charcoal deployment: losslessly, verifiably, and repeatably.

| Term | Meaning |
|---|---|
| **Bundle** | One `.czx` archive (or its exploded directory form, §2.3). |
| **Resource** | One entity type (e.g. `purchase_order`), carried as one NDJSON data file. |
| **Record** | One line of a data file: one entity row plus its envelope (§5). |
| **Manifest** | `manifest.json` — the bundle's contract; the only file whose location and shape are fixed forever by `formatVersion`. |
| **Typed reference** | `<resource>:<uuid>` — the universal reference value form (§6). |
| **Digest chain** | per-file SHA-256 → `checksums.sha256` → `bundleDigest` (§8.3). |
| **bundleDigest** | SHA-256 (hex) of the raw bytes of `checksums.sha256`. The bundle's identity. It is **derived, never stored inside the bundle** (storing it would be self-referential); tools display it, filenames carry its first 8 hex chars, signatures sign the file it derives from. |
| **Producer / consumer** | The software writing / reading a bundle. |

## 2. Container

### 2.1 Archive

- A bundle **MUST** be a ZIP archive. Producers **MUST** write ZIP64 when any limit requires
  it and **SHOULD** use DEFLATE compression. Consumers **MUST** accept STORE and DEFLATE.
- Zip entry timestamps **MUST** be a fixed constant so archives are byte-reproducible; real
  times live in the manifest.
- Entries **MUST NOT** be individually encrypted. Encryption is a whole-file outer layer
  (e.g. `bundle.czx.age`) outside this specification.

### 2.2 Naming

`charcoal-export-<org-code>-<UTC stamp>-<digest8>.czx`, e.g.
`charcoal-export-acme-20260801T104500Z-9c8e7d6a.czx`, where `digest8` is the first 8 hex
characters of the bundleDigest. Informative, not normative — identity is the bundleDigest.

### 2.3 Exploded form

A directory with the same layout is a valid bundle for development, fixtures, and diffing.
Validators **MUST** accept both forms. The digest chain is computed over file bytes
identically in both forms.

## 3. Layout

```
manifest.json            REQUIRED   the contract (§4)
checksums.sha256         REQUIRED   digest of every other file (§8.3)
manifest.sig             OPTIONAL   detached signature over checksums.sha256 (§8.4)
schema/                  REQUIRED   one JSON Schema per resource + enums + fingerprints
  enums.json             OPTIONAL   enum type → valid labels at export time
  fingerprints.json      OPTIONAL   entity → schema fingerprint at export time
  <module>.<resource>.v<n>.schema.json
catalog/                 OPTIONAL   deployment-seeded identities BY NATURAL KEY (§7)
  roles.ndjson           |          never imported as rows; used for reference remapping
  permissions.ndjson     |
  packs.json             |          packs active at source, e.g. ["in","international"]
data/                    REQUIRED   the records: data/<NNN>-<group>/<resource>.ndjson
blobs/                   OPTIONAL   content-addressed binaries
  index.ndjson           |          file metadata → content hash
  sha256/<aa>/<bb>/<hash>|          the bytes; path = hash prefix split
audit/                   OPTIONAL   hash-chained audit entries, whole chains, chain-ordered
controls/                OPTIONAL   declared control totals with tolerances (migration bundles)
quarantine/              OPTIONAL   source rows excluded during migration, with finding codes
resolved/                OPTIONAL   informative effective-state snapshots; never imported
docs/                    OPTIONAL   generated README, archived MappingSpec, changelog
reports/                 OPTIONAL   export report, labels.ndjson (id → display label)
```

Numeric directory prefixes under `data/` are a human-readable ordering hint only. Consumers
**MUST** take file paths and ordering from the manifest, never from filenames.

## 4. `manifest.json`

Pretty-printed UTF-8 JSON (humans read it first). Machine schema:
[`schemas/manifest.schema.json`](https://github.com/charcoal-erp/ember-validator/blob/main/schemas/manifest.schema.json)
in the reference validator (normative for 1.0).

Required top-level fields:

| Field | Type | Meaning |
|---|---|---|
| `formatVersion` | string | `"1.0"`. Consumers **MUST** refuse a major version they don't support, naming the required version. |
| `bundleId` | uuid | Unique per produced bundle. |
| `bundleType` | `"full" \| "subset" \| "delta"` | `subset` marks referentially-closed samples; `delta` is reserved (chained bundles). |
| `profile` | string | Producing profile: `full`, `portability`, `analytics`, `fixture`, `subject`, or `migration`. |
| `createdAt` | ISO-8601 UTC | Export completion time. |
| `producer` | object | `{product, version}` required; `instance`, `deploymentMode` optional. `producer.version` is diagnostic only — **never** a compatibility gate. |
| `organization` | object | `{id, code, companies:[{id, code, name}]}` required; `legalName`, `locale`, `timezone`, `baseCurrency`, `financialYearStart` optional. |
| `resources` | array | One entry per data file, §4.1. |

Optional top-level fields: `consistency` (array, one entry per source database:
`{database, snapshotLsn?, snapshotTxid?, snapshotAt, isolation}`, plus sibling keys
`consistencyMode: "per-db-snapshot"|"quiesced"` and `maxSkewSeconds` inside `options`),
`options` (§4.2), `blobs` (`{count, bytes, index}`), `controls` (`{file}`), `totals`
(`{resourceCount, recordCount, uncompressedBytes}`), `chain` (reserved for deltas).

### 4.1 `resources[]` entry

```json
{
  "resource": "purchase_order",           // singular snake_case resource name
  "module": "procurement",
  "resourceVersion": 3,                   // monotonic integer, per-resource shape version
  "file": "data/050-procurement/purchase_order.ndjson",
  "schema": "schema/procurement.purchase_order.v3.schema.json",
  "recordCount": 48219,
  "sha256": "<hex sha256 of the data file>",
  "dependsOn": ["vendor", "item", "company"],
  "contentClass": "business",             // business|audit|control (informative)
  "scope": {"by": "company", "column": "CompanyId"},   // optional, informative
  "embeds": [],                           // child resources embedded inside records (§5)
  "deleteSemantics": "soft"               // soft|hard|none
}
```

`file`, `schema`, `recordCount`, `sha256`, `dependsOn`, `resource`, `module`,
`resourceVersion` are **required**. `dependsOn` edges **MUST** form a DAG over the bundle's
resources; import order is any topological order of it.

### 4.2 `options`

All optional: `sourceTimezone` (IANA name — the zone naive timestamps were written in;
**required if any resource carries naive timestamps**), `blobsIncluded`, `credentialsIncluded`
(default false), `auditIncluded`, `redactionSaltFingerprint`, `strippedSecretKeys` (array of
settings keys removed at export — tells the target what to re-provision), `idPolicyHint`
(`preserve|remap-deterministic|allocate`), `numberingWatermarks` (`{file}` for subset/migration
bundles), `consistencyMode`, `maxSkewSeconds`.

## 5. Data files and the record envelope

- **NDJSON**: exactly one JSON object per line; every line terminated by `\n` (including the
  last); no header line, no wrapping array, no blank lines.
- Each line **MUST** be in canonical form (§8.1). Records **MUST** be sorted ascending by the
  byte order of their `$id`.
- A resource with zero records **MUST** still ship its (empty) file with `recordCount: 0`.
- A resource that is EMBEDDED in a parent (named in that parent's manifest `embeds`) does
  **NOT** ship a data file of its own, and **MUST NOT** appear in `manifest.resources[]`: its
  rows travel inside the parent's `$embeds` and exist in exactly one place. Both forms are
  legal for the same resource across bundles — a producer may embed or not — so a consumer
  **MUST** read `embeds` rather than assume either shape.

Reserved `$`-prefixed envelope keys; all other keys are domain fields, named **verbatim** as
the producing system's entity properties (Charcoal: PascalCase TypeORM property names — no
renaming, no case mapping):

| Key | Req | Meaning |
|---|---|---|
| `$id` | yes | Typed reference identifying this record: `<resource>:<uuid>`. The resource part **MUST** equal the file's resource. |
| `$v` | yes | The `resourceVersion` this record conforms to. |
| `$op` | no | `upsert` (default) \| `delete` \| `patch`. Full exports emit `upsert` only; `delete`/`patch` are reserved for delta bundles. |
| `$audit` | no | `{CreatedAt?, CreatedBy?, UpdatedAt?, UpdatedBy?, DeletedAt?}` — verbatim source values. Soft-deleted records ARE exported, with `DeletedAt` set. |
| `$source` | no | `{system, externalId}` for records originating outside Charcoal. |
| `$unknown` | no | Bag of fields a tolerant reader did not recognise, preserved for lossless re-export. Consumers **MUST NOT** drop unknown domain fields silently — capture them here and re-emit on export. |
| `$embeds` | no | Child records nested inside this one, as `{"<child resource>": [record, …]}`. Present only on a parent whose manifest entry declares that child in `embeds` (§4.1). Each nested record is a full envelope in its own right — its own `$id` and `$v`, canonical form, sorted by `$id` — with ONE difference: the reference column pointing back at this parent is **omitted**, because `$id` already determines it. A reader reconstructs it from the enclosing record's `$id`. |

**Null discipline:** a field set to null **MUST** be emitted as an explicit `null`; an absent
field means "not provided" (meaningful only under `$op: patch`). Full-export producers emit
every column, nulls included. Empty string and null are distinct and never coerced.

## 6. Typed references

Every reference-bearing value is `"<resource>:<uuid>"`, e.g. `"SupplierId": "vendor:0193…"`.

- Resource names: `[a-z][a-z0-9_]*`. UUIDs: lowercase hex canonical form.
- `grep` for an id finds every touchpoint bundle-wide; polymorphic references need no
  parallel type column.
- **Catalog references** (`role:`, `permission:`) do NOT resolve to data files. They resolve
  through `catalog/` by natural key (§7) — those UUIDs are deployment-local and are remapped
  at import.
- **Identity-audit references** (`user:` values inside `$audit`) MAY dangle (the user may not
  travel in the bundle); validators report these as warnings, not errors. Every other typed
  reference **MUST** resolve to a record in the bundle (or, at import time, to a target-side
  record under the declared ID policy).
- A uuid-valued domain field that is intentionally NOT a reference (external correlation ids)
  is carried as a bare uuid string without a prefix.

## 7. `catalog/`

Deployment-seeded identities whose UUIDs differ per deployment. Never imported as rows; used
to resolve typed references by **natural key**.

- `roles.ndjson`: `{"$id":"role:<sourceUuid>","Name":…,"IsDefaultRole":…,"OrganizationId":…}`
  — natural key `Name` (per organization).
- `permissions.ndjson`: natural key `(Name, ServiceName, Type)`; carries the source UUID in
  `$id` the same way.
- `packs.json`: array of pack codes active at the source. A consumer **MUST** refuse to import
  data whose resources require a pack (side-table resources) that is not active on the target.

## 8. Canonicalization, integrity, trust

### 8.1 Canonical JSON

Every NDJSON line and every schema file **MUST** be serialized canonically:

- Object keys sorted lexicographically (by UTF-16 code units), recursively.
- No insignificant whitespace. UTF-8, no BOM. LF line endings only.
- Number formatting per ECMAScript `JSON.stringify` (JCS/RFC 8785-compatible). Producers
  **SHOULD NOT** emit non-integer JSON numbers at all — fixed-point values travel as strings
  (§9).

Consequence: two exports of unchanged data are byte-identical, `git diff` on fixtures is
meaningful, and round-trip fidelity collapses to a digest comparison.

### 8.2 Timestamps and dates

`date` values: `"YYYY-MM-DD"`, never a timestamp. Zone-aware timestamps: ISO-8601 UTC with
`Z`. Zone-naive timestamps: ISO-8601 without zone suffix, interpreted in
`options.sourceTimezone`.

### 8.3 The digest chain

```
per-file SHA-256  →  checksums.sha256  →  bundleDigest (= sha256 of checksums.sha256)
                                       →  manifest.sig (signature over checksums.sha256)
```

`checksums.sha256` format: one line per file, `<64 hex sha256><SPACE><SPACE><path>`, sorted
by path (byte order), LF-terminated. It **MUST** cover every file in the bundle except itself
and `manifest.sig`.

### 8.4 Signing (optional in 1.0)

`manifest.sig` is a detached JWS (Ed25519, `alg: "EdDSA"`) over the raw bytes of
`checksums.sha256`, with two slots: `producer` (instance identity, required when signing) and
`custodian` (operator, optional). Key distribution and verification policy are deployment
concerns outside this document; validators verify structure and, when given a public key,
the signature.

## 9. Type fidelity

| Source type | Bundle form | Rule |
|---|---|---|
| Fixed-point / money / `NUMERIC` | JSON **string**, scale preserved (`"1711000.00"`, `"12.500"`) | Never a JSON number — IEEE-754 cannot round-trip it. Trailing zeros are significant. |
| `bigint` | string | Exceeds 2⁵³−1. |
| int / smallint | JSON number | |
| boolean | JSON boolean | |
| uuid | string (typed ref §6 if classified as a reference) | |
| `date` | `"YYYY-MM-DD"` string | A shifted FY boundary is a compliance incident. |
| timestamp (naive) | ISO string, no zone + `options.sourceTimezone` | |
| timestamptz | ISO string with `Z` | |
| time | `"HH:MM:SS"` | |
| interval | ISO-8601 duration | |
| enum | string label; all labels dumped to `schema/enums.json` | Lets a consumer distinguish "unknown value" from "removed value". |
| json/jsonb | inline nested JSON, canonicalized | Key order not significant. |
| array | JSON array | |
| bytea / files | never inline — `blobs/` + `"blob:sha256-<hex>"` reference | |
| derived (tsvector, generated, caches) | not exported | Rebuilt post-import. |

## 10. Blobs, audit, controls, quarantine

- **Blobs** are content-addressed: path `blobs/sha256/<h[0..2]>/<h[2..4]>/<h>`; identical
  content stored once. `blobs/index.ndjson` records carry file metadata and
  `"Content": "blob:sha256-<hex>"`. Validators verify every referenced blob exists and its
  bytes hash to its name.
- **Audit** entries are hash-chained per (EntityType, EntityId) with `SequenceNumber`,
  `PreviousHash`, `Hash`. Producers **MUST** export whole chains in order; consumers **MUST**
  import them verbatim and verify chains post-import. Chains are incompatible with any
  transformation (subsetting a chain, date rebasing).
- **Controls** (`controls/control-totals.ndjson`): records
  `{control, basis, legacyValue, tolerance, note?}`; a consumer's verify stage **MUST** check
  loaded data against them and require explicit, attributed acceptance of any variance.
- **Quarantine** (`quarantine/<resource>.ndjson`): source rows a migration excluded, each with
  `$findings: [<code>…]`. Informative — the honest record of what was NOT migrated.

## 11. Versioning and compatibility

Three independent axes:

| Axis | Field | Changes |
|---|---|---|
| Format version | `formatVersion` | Rarely; SemVer. Envelope/layout/reference-syntax changes are **major**. |
| Resource version | `resourceVersion` / `$v` | Whenever that entity's shape changes; monotonic integer; consumer migrates records `$v → current` through a registered chain, in memory, before validation. |
| Producer version | `producer.version` | Every release; diagnostic only. |

Contract: **tolerant reader, strict writer.** Writers emit exactly the current shape. Readers
accept anything they have a migration path for; unknown fields go to `$unknown` (§5); a
missing migration link is a hard, precisely-named failure. A `formatVersion` newer than the
reader supports **MUST** fail clearly — never a best-effort partial read.

Support window: an importer **MUST** accept any bundle produced in the preceding 36 months
(enforced by golden bundles in CI, not by intent).

## 12. Profiles (informative)

`full` (everything, real values, blobs, watermarks) · `portability` (customer-owned data
only) · `analytics` (deterministically pseudonymized, blobs excluded) · `fixture` (sampled +
masked + date-rebased; audit excluded) · `subject` (one data subject across all modules) ·
`migration` (produced by Import Studio: `allocate` id-policy hint, `controls/`, `quarantine/`,
archived MappingSpec under `docs/`).

## 13. Conformance and validation stages

A bundle is **conformant** when the reference validator's stages 0–6 pass:

```
0  Container    zip/directory readable; manifest.json + checksums.sha256 present
1  Digests      every checksums line matches its file; no uncovered files; bundleDigest computed
2  Manifest     schema-valid; formatVersion supported; resource files exist; dependsOn is a DAG
3  Records      valid JSON per line; canonical bytes; envelope keys; $id resource/file match;
                sorted by $id; recordCount and per-file sha256 match the manifest
4  Schemas      every record validates against its resource's JSON Schema
5  References   every typed reference resolves in-bundle (catalog refs → catalog/;
                $audit user refs may dangle → warning)
6  Blobs        every blob reference present; blob bytes hash to their address
```

Signature verification (stage S) runs when a key is supplied. Producers **MUST** produce
conformant bundles; consumers **MAY** rely on conformance after verifying it — never before.

## 14. Governance and change process

**Ownership.** This specification is owned by Charcoal ERP. It is published so that anyone can
write software that reads or writes Ember bundles, without permission and without a commercial
relationship.

**Versioning.** The three version axes are normative and independent (§11). This document
describes `formatVersion` **1.0**, frozen 2026-08-01. A frozen version never changes meaning:
corrections that alter what conformant software must do produce a new version, not an edit.
Editorial fixes that change no requirement (typos, clarifications, added examples) may be made
in place and are listed in the reference validator's CHANGELOG.

**Proposing a change.** Open an issue on the [reference validator repository](https://github.com/charcoal-erp/ember-validator)
describing the problem the change solves, the bundles it would affect, and whether existing
producers or consumers would need to change. Changes that would make an already-issued bundle
unreadable are the ones that get the most scrutiny — see the support window below.

**The support window.** An importer MUST accept any bundle produced in the preceding **36
months** (§11). Charcoal enforces this mechanically rather than by intention: sealed golden
bundles, one per format era, are committed to the reference validator repository and every
build asserts that they still verify and are still readable at current resource versions. A
version bumped without a registered migration fails the build. If you are writing a consumer,
you are welcome to use the same goldens as your own regression corpus.

**Conformance claims.** Software may describe itself as producing or consuming conformant Ember
bundles when the reference validator's stages 0–6 pass (§13). "Validated by the reference
validator" is a statement about the bundle, not an endorsement of the software by Charcoal.
